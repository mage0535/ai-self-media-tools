# Cinema Render Contract

Every final video is described by `scene_manifest.json`. It is generated by
`scripts/video_toolchain_runner.py` from the existing `visual_recipe.json`,
cards, resolved visual assets, and Shotcraft motion plan.

The manifest is deliberately renderer-neutral. A renderer may implement a
card sequence, a multi-shot composition, or an external edit, but it must keep
the following evidence for every scene:

- narration and matching subtitle;
- the visual claim being made;
- the resolved asset and its matching reason;
- independent background, subject, text, and transition motion;
- a platform duration policy.

## Main Pipeline

The standard runner writes and validates this sequence before rendering:

1. `visual_recipe.json`
2. `cards.json`
3. `scene_manifest.json`
4. `pre_render_gate.json`
5. rendered artifact, motion evidence, and artifact gate

For TikTok and YouTube short-form plans, a rendered artifact over 60 seconds
is rejected. The final output must also retain the existing BGM fingerprint,
subtitle, audio, cover, and visual-recipe checks.

## External Cinema Renderers

An experimental or skill-based renderer must not directly hand off an MP4.
It must produce the same `scene_manifest.json` and `bgm_source.json`, then run:

```bash
python scripts/verify_cinema_delivery.py \
  --video final.mp4 \
  --scene-manifest scene_manifest.json \
  --bgm-source bgm_source.json \
  --output cinema_delivery_gate.json
```

The BGM metadata requires source, license, fingerprint, and a content-fit
reason. A fixed music URL or a reused track cannot be treated as a valid
delivery path. External renderers must also supply stored motion evidence and
subtitle sampling evidence; printing those checks to stdout is not proof.

## Migration Rule

`scene_manifest.json` is the delivery timeline source of truth. It is derived
from the existing visual design and motion planning inputs, while
`visual_recipe.json` remains a compatibility artifact for older tools and
`segment_motion_evidence.json` remains post-render proof. Do not create a
second independent timeline format.

## TTS Contract

`display_text` remains the source for subtitles and publish copy. Before any
provider call, `scripts/voice_engine.py` compiles it into provider-safe
`tts_text` using `config/pronunciation_dictionary.json`. The output records the
rules used, provider, voice, duration, and unhandled Latin tokens in
`tts_config.json` and `tts_normalization_report.json`.

When `scene_manifest.json` exists in the same output directory, measured TTS
segment durations are written back to each scene's `start`, `end`, and `audio`
fields. A scene-count mismatch fails closed. This keeps the manifest as the
only timeline source; `visual_recipe.json` remains a derived compatibility
artifact.
